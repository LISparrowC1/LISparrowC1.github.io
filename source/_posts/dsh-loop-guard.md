10 月中旬，DSH 上一个长任务跑到第 31 轮，输出变成一整屏「好。（输出。）」：模型没报错、没停，只是把同一句话反复刷出来。当时的请求上下文已经涨到约 30 万 token，光工具 schema 就占 4.8 万。这是长上下文下的解码退化，工具调用没有重复，流式阶段没有任何东西拦它，它一直刷到撞上输出上限。

上下文的膨胀和这条退化是配套出现的：token 一直在涨、一直在输出，从外面看「还在工作」，实际没有任何新信息。这类失效的难点是没有报错、没有异常的调用栈，流式阶段也不触发任何「重复工具调用」提醒，只能靠流本身的内容特征去识别。

![dsh-loop-guard 封面](images/cover.webp)

DSH 自带一个 `dsh-repeat-tool-reminder`，但它只认参数完全相同的工具调用，而且只提醒、不阻止。缺的是另外三格：近似重复的工具调用、A→B→A→B 的工具循环、以及没有进展的一轮。dsh-loop-guard 补的就是这三格。

## 三种看起来还在工作的失败

| 失败形态 | 从外面看 | 实际发生的事 |
| --- | --- | --- |
| 输出退化 | 模型一直在输出 | 同一句话反复刷，上下文越长越容易 |
| 工具打转 | 工具一直在执行 | 同一目标换 offset 反复读、同一条命令反复跑、A→B→A→B |
| 失控的一轮 | 回合一直没结束 | 步数、时长、输出量持续涨，不收敛 |

三种的共性是「看起来还在工作」，比报错更危险：报错至少会停，这些形态却会一直消耗 token、API 配额和人的等待时间。guard 的目标是判断有没有进展：有进展放行，没进展就停住当前这件事。

## 只挂公开接缝，不改 agent loop

| 接缝 | 挂载方式 | 用途 |
| --- | --- | --- |
| `llm/stream` | 瀑布，prepend | 包住分片流，实时检测重复，用一个终止错误分片结束这次尝试 |
| `agent/request-error` | 瀑布 | 接管自己的失败码，重跑该步，且有次数上限 |
| `agent/pre-step` | 瀑布 | 跟踪轮次边界 |
| `tools/post-execute` | 瀑布 | 跟踪近似重复的工具链，注入模型可见的提醒，超硬阈值取消本轮 |

不碰 agent loop 是刻意的。改 loop 就得 fork DSH，每次升级都要跟着重打补丁；这四个是官方文档里的扩展缝，插件只在缝上挂监听，加载器卸载时一起清掉。代价是能做的事有限：guard 只能「结束这一次尝试」或「取消本轮」，改不了循环本身的调度。

Cordis 的「瀑布」指一组中间件按序执行、任意一个都能提前返回结果，`prepend` 是把监听器插到链的最前端。`llm/stream` 用 `prepend` 的原因：监听器要先于其他消费方看到每个输出分片，检测到重复时返回一个终止错误分片把这次尝试结束，后面的监听器就收不到后续分片。

![三种失控与 guard 的拦截流程](images/flow.webp)

另一个边界要先划清：带 `purpose` 字段的辅助调用不归 guard 管。`isGuardedRequest` 用 `purpose` 字段过滤：给会话起标题（session-title）、压缩上下文（compaction）这类辅助调用带 purpose，一次性调用没有会话身份，这两类都放行。截断一次标题生成或上下文压缩没有意义，还可能把这类后台动作打断。

## 周期检测与滚动哈希分片

重复检测跑在一个 4096 字符的滚动窗口上，两个检测器互补，因为它们漏检的输入正好相反。周期检测抓住短而顶到末尾的重复，但要求单元完全相同、且一路延续到窗口尾部，成段重复如果没对齐尾部或中间夹了别的内容就漏掉了；滚动哈希分片不看位置，只要某一段在整个窗口里占了足够大的比例就触发，代价是认不出「一句很短的话反复出现」：短句覆盖的总面积太小，到不了覆盖率阈值。

**周期检测**抓「短单元顶到窗口末尾」。从窗口尾部往回找任意长度的单元（6 到 80 字符），要求连续重复至少 8 次、总跨度至少 400 字符。每个候选单元先比最后一个字符，对不上直接跳过，省掉逐个切片；单元长度还有 `窗口长度 / 8` 的上限，不会越界。「好。（输出。）」这种短句无限重复由它负责。

**滚动哈希分片**抓「某一段覆盖了窗口的大部分」。固定 64 字符的切片，用 base 131 的滚动哈希在每一个偏移上计数，再对计数最高的几个候选做精确子串验证：哈希只提名，真匹配才作数，碰撞不会造假命中。覆盖率是「该片段所有出现的并集长度 / 窗口长度」，默认要求至少 4 次、覆盖 0.5。一个段落重复几遍就把窗口填满，一句偶尔回环的话远达不到阈值。

```text
// lib/detector.js — 分片参数
const SHINGLE_LENGTH = 64
const SHINGLE_BASE = 131
```

窗口不是越大越好：`windowChars` 默认 4096，会跟 `minSpanChars * 2` 取较大值，保证阈值语义不被窗口截断。分片扫描要遍历整个窗口，所以每收到 32 个新字符才跑一次；如果每来一个分片就全窗口扫一遍，窗口塞满之后会越来越慢。按 32 字符批量触发，每个分片的均摊成本是常数。reasoning 流同样消耗 token，默认也纳入检测。

两个文本检测器只看最近 4096 字符的滚动窗口，不看整轮历史，「进展」由此被定义成「最近一段输出还在产生新内容」。只要新输出不在重复旧内容，文本检测器就不介入；一旦最近的输出进入重复模式，说明这一轮大概率在原地打转。窗口小，判断快、内存占用固定，代价是更早之前的重复会随窗口滚出去，周期检测的 `minSpanChars` 下限和分片检测的覆盖率阈值就是为了在「滚出去之前」抓到一次。

工具调用的参数不参与重复判定，也不计入输出预算。写文件、跑长命令属于真实工作：`chunkWeight` 只统计 `text-delta` 和 `reasoning-delta` 的文字，`tool-call-delta` 一律不计。

```text
// lib/guard.js — 只统计模型文字，工具参数不计
function chunkWeight(chunk) {
  return typeof chunk.text === 'string' ? chunk.text.length : 0
}
```

## 分片检测的相位缺陷

第一版分片检测按固定步长取样：每隔 16 个字符取一个 shingle 起点。单测全过，但有一个漏洞：如果重复单元的周期不是步长的整数倍，相邻的重复会落在不同的 shingle 上，计数就散了。

比如一个 6 字符的单元反复重复，按 16 步长取样，每次取到的 64 字符窗口起点都错开 6，互相之间没有一个 shingle 完全相同，detector 就永远看不到「它在重复」。周期检测能兜住短单元，但成段重复、且周期错开步长的情况会漏。

修法是改成滚动哈希、在每一个偏移上计数，再把计数最高的几个候选用精确子串确认。滚动哈希让逐偏移计数保持 O(窗口长度)，精确验证让哈希碰撞不可能产生假命中。改完加了一条测试：一段 400 字符的随机正文先把窗口填满，再接 20 遍同一段话，确认窗口饱和之后仍然会触发。

## 花费熔断误停正常长任务

回合刹车（brake）一开始是四项硬上限：单轮最多 60 步、最多 30 分钟、每小时最多 240 次调用、单轮模型输出最多 20 万字符。这台机器上很快把 brake 整体关掉了：它按「整轮累计」计数，一个合法的重构就能超过 60 步或 30 分钟，误停比它防的失控更烦。

触发时产生 `budget-refused`、`budget-output` 事件。刹车和两个循环守卫是分开的：`brake.enabled: false` 关掉刹车，输出刷屏拦截和工具打转拦截照常工作。本机 profile 里这条开关的注释写着「按整轮累计计数，搞大项目时会误停」，这台机器因此把 brake 关掉了。它被标成「可选」也是这个原因：防的是「无人看着时烧钱」，代价是长任务容易被误停。

## 近似工具链：提醒与硬停

工具打转的判定关键在「目标」怎么抽。DSH 自带的 repeat-tool-reminder 比较参数完全相同的调用，换个 offset 就骗过它。guard 的做法是从参数里挑出标识目标的那几个字段（`path`、`file_path`、`command`、`query`、`job_id` 等）忽略只微调动作的字段（offset、limit）。`read(path=a.md, offset=1)` 和 `read(path=a.md, offset=900)` 抽出来的目标相同，才计为近似重复。反过来，`read(path=a.md)` 和 `read(path=b.md)` 抽出来的目标不同，不算重复；读两个不同的文件属于正常的分头工作。

```text
// lib/guard.js — 目标字段，忽略 offset/limit
const TARGET_FIELDS = ['path','file_path','filePath','pattern','query','url','command','script','job_id','jobId','session','sessionId','id','name','target']
```

抽目标之前先做规范化：参数深层键排序（`{a:1,b:2}` 和 `{b:2,a:1}` 归一到同一种）、折叠空白、截断到 200 字符，最终 key 再截到 400 字符。换了字段顺序、多了空格不会造成误判。

连到第 5 次（fuzzyAdvisoryAt）往对话里注入一条模型可见的提醒；连到第 12 次（hardStopAt）直接取消本轮。先提醒再硬停，给模型一次自行调整的机会，也避免一上来就误杀一个只是碰巧重复了几次的正常任务。A→B→A→B 的循环靠最近 12 条历史单独识别，周期 2 到 4、重复 3 轮就提醒。`todo_write` 和 `job_output` 默认排除。

## 配置的两个入口与事件日志

profile 的 `cordis.patch.yml` 只在启动时读，改完要重启 DSH。为了调参不重启，guard 还读一个实时覆盖文件 `$DSH_HOME/loop-guard/config.json`，每次决策前现读、按字段合并覆盖在 patch 配置之上，下一次模型调用就生效。临时试阈值就写 `{"dryRun": true}`（只记录不动作），确认误报再调高 `minRepeats` 或 `minShingleCoverage`。

`locale` 只管给人看的文字：结束回合的错误、对话里的守卫提示、事件日志的 `reason` 字段；发给模型的提示永远是英文，所以模型行为不随界面语言变化。

所有决策都落一条 JSONL 日志（`$DSH_HOME/loop-guard/events.jsonl`），`kind` 标出是哪种拦截、`reason` 引用被判重复的原文片段。怀疑误切时先看这条日志里引用了哪段文字，再决定调哪个阈值。日志只追加、会持续变大，不需要历史时自行删。

## 升级 DSH 之后的适配

0.1.1 相对 0.1.0 没有行为变更，改动来自 DSH 换了兼容性判定。之前只看 peerDependencies，0.2.1-alpha.3 起先读 `engines.dsh`，没有才回退 peer 依赖。0.1.1 声明 `engines.dsh: ^0.2.0-rc.2`，整个 0.2.x 系列（含预发布）都能通过检查。

真正要核对的是四个接缝在新版还在不在。把 0.2.2-rc.5 的 `dsh-llm`、`dsh-agent`、`dsh-agent-loop`、`dsh-tools` 拉下来逐个 grep：`llm/stream`、`agent/pre-step`、`agent/request-error`、`tools/post-execute` 四个事件全在，`createUserMessage` 也还从 `dsh-llm` 导出。所以 0.1.1 不改代码，只更新 engines 声明和 README 的实测版本。升级 guide 里相关的四条（llm-error-builtin-codes、llm-request-purpose-declarations、plugin-engines-dsh、tool-executor-plugins）也都标了「无需改插件」。0.1.1 是否只有 engines 声明变化、没有任何代码改动，依据发版说明与升级会话，没有逐行 diff 两个版本（未验证）。

## 安装

一条命令，`<profile>` 换成实际跑的 profile 名：

```bash
dsh plugin --profile <profile> add github:LISparrowC1/dsh-loop-guard
```

手动装也行：把包复制进 profile 的 node_modules，再在 `cordis.patch.yml` 加一条 `- insert:` 的 entry。两种方式只能选一种：两个 entry 会把插件挂载两次。手动复制不进 lockfile，之后在那个 profile 跑 `pnpm install` 可能把它清掉。

## 边界

它不判断任务难不难，只看有没有进展，所以一个「正确但就是慢」的任务也可能被 step 上限拦下，本机因此把 brake 关掉。被 guard 结束的回合会以明确的错误码收尾，最多按配置重跑一次（重试按 agent、轮次、步骤记数，换轮清零）；重试用尽就把被判重复的片段连同重试次数一起交回。22 个测试覆盖检测算法、流包装、重试预算、工具链、dryRun 和实时覆盖。阈值默认取保守值，「触发后零误报」是本机观察、不写成硬统计；「会不会误切」没有测试能回答，只能靠 dryRun 观察一段时间再收紧。第 31 轮的现场细节来自事后复盘，原始会话已不保留（未验证）。
