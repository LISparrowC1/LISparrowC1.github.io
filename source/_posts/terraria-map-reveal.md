泰拉瑞亚更新到 1.4.5.8 之后，存档格式整个变了：`.map` 文件版本号跳到 326，开头多了 `relogic` 魔数，数据体换成 raw DEFLATE 加按行 RLE。网上针对 1.4.4 的地图点亮教程全部失效。这个工具不装模组，改走另一条路：把游戏读写 `.map` 的逻辑逆向出来，按原版格式写文件。

真正的难点在验证：怎么证明写出来的文件能被游戏正确加载。

## 反编译要读的三个类

不装模组就得自己会写这个格式。用 ILSpy 反编译 `Terraria.exe`，拎出三个类来读：`WorldFile`（`.wld` 的读写）、`MapHelper`（地形到地图类型的换算）、`WorldMap`（`.map` 的读写）。游戏源码里每条不明显的规则，都照着它的逻辑翻译，再在代码里注释出自哪段，方便游戏更新后重新对照。

`.wld` 有一个现成的强校验：文件头里存了每个区块的绝对偏移，瓦片区块解析结束时指针必须正好落在下一个区块的开头。对不上，说明对格式的理解有偏差。这个校验和内容无关：只要偏移对不上，就能在解析出错的第一时间断定理解有偏差，避免把错数据带进后续步骤。自检第一项就跑这个。

`.map` 的数据体是 raw DEFLATE：zlib 去掉头和校验（`wbits=-15`），既不是 zip 也不是 gzip。一开始按普通 zlib 解，解出来一堆垃圾。解压后是按行的 RLE，每行从 0 铺到 8400（一个 8400×2400 的大世界）。瓦片流是 x 方向为主的：一个头字节的高两位是重复计数，让连续相同的方块只占一条记录。只有被「重要性位图」标记的方块类型，后面才会多跟 4 字节 framing 数据；这个位图得先从文件头读出来，否则遇到第一个这种方块就会整体错位。

## .map 只存探索记录

`.map` 文件本身不含任何地形，只存两样东西：每个格子「是否已探索」的光照值，和一张把方块类型映射到显示颜色的类型查表。真正的方块、墙壁、液体都在 `.wld` 世界文件里。

点亮的做法是：解析 `.wld` 里的真实地形，按游戏 `MapHelper` 自己的逻辑算出每个格子该显示成哪个 map 类型，再写回 `.map`。地形在 `.wld` 里按类型平面分开存：tile、wall、liquid，以及 sky/dirt/rock 各 256 种；tile 的 flat 编号从 1 到 1064，wall 有 367 种。这样没去过的地方显示的是真实的矿脉、洞穴、浮空岛、地狱，地图没有被刷成一片白。另有一个 `--dark-air` 开关：只亮有地形的格子、未探索的空气保持黑，给只想看矿脉走向、不想要整片天空全白的人。

还有一个隐蔽点：`.map` 跟着角色走。游戏用角色目录去拼地图文件名，`.map` 与世界文件分开存放。旧世界的文件名是世界 ID，1.4.5 生成的新世界用 GUID 当文件名：`generator_version` 超过一个阈值就切 GUID。这条规则直接影响工具能不能找到要改的那张地图。

## 写文件前的两道校验

写 `.map` 前有两道校验，少任何一道都可能写出坏文件：

- 版本号：文件头 `int32`，1.4.5.x 是 326。不是 326 直接报错不写；比 326 大也报错，说明游戏又更新了格式。
- 世界 ID 和尺寸：地图 header 里存着 `world_id` 和 `maxTilesX`/`maxTilesY`，必须和世界文件一致。ID 对不上（地图属于另一个世界）就跳过；尺寸对不上直接报错，不会硬写一个宽高不符的文件。

版本号后面还跟着 20 字节的 FileMetadata：`relogic` 魔数、文件类型字节、每次保存自增的修订号和收藏位。写文件时修订号要 +1，和游戏自己保存的节奏一致，否则读档时可能被判定成旧文件。

落盘走「写临时文件再原子替换」：先写 `.tmp`，再用 `os.replace` 覆盖原文件，避免写到一半断电留下半截坏文件。加上「写之前备份、写完回读校验」，写坏的概率才压下去。回读会把刚写的数据再解码一遍，核对类型、光照、颜色三张网格和写入前完全一致，才算完成。全亮后文件反而更大：一张 1,605,293 字节的地图点全后涨到 3,251,984 字节（约 1.6 MB → 3.25 MB），因为未探索区域原本被压缩成「跳过」，全亮后每个格子都得记一条。

## RLE 里的光照字节

这套格式的难点在验证侧。自检逻辑是交叉验证：把游戏自己写的地图解码出来当基准，再把同一张世界的真实地形按工具的逻辑推算成 map 类型，两边逐格比对。游戏写出的地图是格式层面的基准事实，推算结果是被测对象，两者一致才说明解码和类型映射都对。第一次跑一张已探索 86% 的大图，一致率只有 9.81%。

9.81% 这个数字指向错位：如果是地形类型算错，偏差应当是大范围的系统性偏移，实际数字却接近随机的一半对一半错。又加了几条不变量去扫错位点：某些类型只可能出现在特定高度，比如地表背景类型不会出现在地下，解码一旦违反就说明流已经错位了。借这个不变量把错位缩小到第 187 行（日志标作 `first bad row: y=187`）。接着 dump 每一行解析出来的格数，立刻看到问题：某一行解析出 43691 格，实际只有 8400 格，日志里出现 `run overruns the row`。

问题出在 RLE 的运行长度记录。一条记录 = 头字节 + 可选的颜色/类型/光照字节 + 运行长度。关键细节是，当一条记录带光照字节时，run 里多出来的每一格都要各自跟一个光照字节。判断「这条 run 带不带逐格光照字节」用的是头字节里的一个位，但那个变量在 run 循环里被覆盖了：该读 N 个光照字节时读成了别的数，流从第一处带光照的长 run 开始整体错位。修法是把这个判断变量的作用域改到每条记录独立，不在 run 循环里覆盖。

改掉之后，游戏自己的地图能完整读到最后一个字节（2,882,323/2,882,323），和世界推算的类型一致率 98.56%（3,092,107/3,137,194）。剩下 1.44% 逐对 dump 确认过：都是同一种方块的配色分支和地图里过期的旧记录，与地形映射无关。

## copy2 保留 mtime

备份用 `shutil.copy2` 复制原文件成 `<原文件名>.map.bak-YYYYMMDD-HHMMSS`。写完地图后会问一句「要不要恢复」，恢复就是把本次备份复制回去。测试时输出「已恢复」，但下一行校验写的是「恢复后地图哈希与备份一致: False」；恢复根本没用对文件。

给恢复函数加了探针，打印它拿到的路径和时间阈值，发现它按「mtime 晚于运行开始时间」去找本次备份，结果一份都找不到。根因是 `copy2` 会保留源文件的修改时间，所以备份文件的 mtime 还是点亮前那个时间，早于运行开始时间，永远匹配不上。

改成按「运行前后的文件名差集」找本次备份（`set(glob(...)) - backups_before`），恢复后哈希与备份一致才转成 True。这个坑和格式没关系，纯粹是文件 API 的细节，但它发生在最危险的「恢复」路径上。

## 世界创建时间、内存与 PowerShell 提示

除了两个大的，还有几个开发时的细节：

- 世界创建时间差了 8 小时：`.wld` 里存的创建时间是「UTC 刻度却标成 Local」的畸形时间，直接读出来会偏一个时区。显示前拿它和文件自己的创建时间比对，选更接近文件系统的那个读数。
- 内存：一个 8400×2400 的世界有 2000 万格，编码时按行压、每积满 1 MB flush 一次，没有把整张图同时压进内存。
- PowerShell 提示漏了：`.ps1` 里的 `Read-Host` 提示直接写控制台 host、不走 stdout，在非交互环境跑会把提示漏到用户终端，测试时要用 `-Choice` 参数跳过交互。

## 64 种装饰方块

交叉验证里那 1.44% 的残差，一开始担心是某种方块类型映射错。逐对 dump 后确认：记录的是 224，算出的是 223，两者属于同一个方块的选项 1 和选项 0。全表统计下来，带多个配色选项的方块恰好 64 种：树、仙人掌、晶簇、各种生物群系变体。

预览图渲染用的配色表来自 `MapHelper.Initialize()`：那里有几千行 `array[n][m] = new Color(...)`，用正则从反编译出来的 `MapHelper.cs` 里提取成 `map_palette.json`。游戏更新后配色变了，重跑一次 `--rebuild-palette` 就行。提取时顺便统计出带配色分支的方块正好 64 种。

这些方块的配色取决于游戏里它实际长成的样子（树的品种、晶簇的颜色），地图文件里存的是「选项号」。从世界文件推算不出该用哪个选项，所以统一用每种方块的默认色。地形、矿脉、墙壁、液体完全一致，只有这 64 种装饰方块的个别颜色和游戏逐个探索出来的略有差别。

## 最外圈 40 格

点亮前这张大世界只有 3,137,194 格被探索（15.6%），工具写完后回读能到 20,160,000/20,160,000，但进游戏后最外圈还是黑的。这一圈黑的来源是游戏自己的读档行为：`WorldMap.ClearEdges` 每次读档都会清掉最外 40 格，走进附近才会重新点亮。所以「全亮」永远到不了字面意义的 100%，这是格式之外、游戏行为层面的硬限制。

## 清理进回收站

清理功能删的东西严格限定三类：人物（`.plr` 加它的地图）、单张地图（`.map`）、备份（`.bak-*`）。世界文件 `.wld` 从不进清理范围。删除一律走 Windows 回收站：优先用 `send2trash`，没有就退到 `SHFileOperationW` 的 `FO_DELETE | ALLOW_UNDO`，删错了能还原。改存档的工具操作上容易误删，回收站把代价压到最低。

## Steam 云存档

旧文发出去两天后，工具在 Steam 云存档的角色上找不到文件。云存档的实际位置是 Steam 安装目录下的 `userdata\<账号>\105600\remote\players` 和 `worlds`（105600 是泰拉瑞亚的 App ID），与「文档\My Games\Terraria」无关。地图跟着角色走，所以云角色配本地世界时，地图也躺在云目录里。

这里有两个和覆盖顺序有关的坑。一是写云存档前必须完全退出 Steam，否则 Steam 的同步可能把改动覆盖掉；改完由 Steam 在下次启动时上传。二是 Steam 安装目录会从注册表和常见路径各拿一次，同一个路径大小写或斜杠不同，云角色和世界就会重复列出，必须用 `normcase(normpath())` 去重。

还有「本地/云端同名冲突」：同一个角色名在本地和云各有一份时，表格会用「来源」列标出「本地 / 云」，看清改的是哪份。改错位置，轻则改了没生效，重则 Steam 同步时把云端的旧地图拉回来盖掉新地图。

## 限制

- 最外圈 40 格永远到不了 100%，这是游戏读档时的行为。
- 64 种装饰方块用默认色，个别颜色和逐格探索有差异。
- 角色难度要从加密的 `.plr` 头部读。角色文件是 AES-128-CBC，key 和 IV 都是 `h3y_gUyZ` 的 UTF-16LE 字节；这个字符串游戏写死在源码里，NoPadding。名字和难度就在解密后的开头。解密依赖 `cryptography` 或 `pycryptodome`，两个都没装时难度显示「未知」，不影响点亮。
- 游戏更新到更高版本、存档格式再变，工具会明确报错，不硬写。

如果哪天 1.4.6 又改了格式，重新反编译对一遍就行；「解游戏自己写的地图、和世界推算的类型交叉验证」这条自检链路已经搭好，格式有没有改、改在哪，跑一次就知道。源码在 [GitHub](https://github.com/LISparrowC1/TerrariaMapReveal)，MIT 协议。
