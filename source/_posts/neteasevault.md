插上耳机，Windows 把默认输出切到「耳机」，程序里的歌却还在扬声器里响；停掉再点播放，还是扬声器。这不是下错了歌，是下对了、播不出来。1.2.10 之前最气人的 bug 就是这个。

这篇写 1.2.9 到 1.2.12 之间我修掉的几处真实的坏法，顺带把「怎么实现、哪里会坏、怎么定位」说清楚。NeteaseVault 干的事一句话：把网易云「我喜欢的音乐」同步到本地，逐首下载、校验、清洗，目标是十年后这些文件还能直接播放，而且没有一首是错的歌。

## 默认设备切走之后，声音留在了原地

先说清现象。不插耳机启动程序，点一首歌开始播；插上耳机，Windows 声音设置里把默认输出切到耳机；扬声器继续响，耳机无声。把播放停掉再点播放（`stop()` 再 `play_file()`）依旧如此。同一时刻用别的播放器播同一个文件，声音正常走耳机。反向确认：杀掉进程、耳机仍是默认设备时重启，声音就走耳机。

所以结论是：输出目标由「进程启动那一刻的默认端点」决定，整个进程生命周期内不再解析。

我当时先怀疑解码或文件本身的问题，用别的播放器对照之后排除掉了。真正定位靠两件事：一是那两处创建播放器的代码，二是全仓库搜了一遍设备相关词。

```python
# app/ui/player_bar.py —— 只传 parent，不指定设备
self._player = QMediaPlayer(self)
self._audio = QAudioOutput(self)
self._player.setAudioOutput(self._audio)
```

`QAudioOutput(self)` 只传父对象、没指定 `QAudioDevice`，Qt 在构造这一刻用 `QMediaDevices.defaultAudioOutput()` 绑定了当前默认端点。播放条是主窗口常驻部件，同一个 `_audio` 实例贯穿每次播放，等价于进程级绑定。候选试听（审批对话框里的试听按钮）是第二处，写法一模一样。而 `app/` 下 47 个 `.py` 文件里 `[Dd]evice`、扬声器、耳机，零命中——从头到尾没有任何代码显式指定过设备。

修复分两步，中间我走错过一次。1.2.10 我先写的是「显式绑定默认设备」：加一个 `FollowDefaultOutput` 帮助类（`app/ui/audio_route.py`），监听 `QMediaDevices.audioOutputsChanged`，默认设备变化时重建 `QAudioOutput`，重绑前先取走 source、position、volume、mute 和播放/暂停状态，换完再恢复；同时接上 `QMediaPlayer.errorOccurred`，设备被占用或不存在时弹提示，不再静默无声。

但有人问了一句「某些软件支持按应用指定输出设备，这个能适配吗」，我才发现显式 `setDevice(默认设备)` 是错的：`QMediaDevices.defaultAudioOutput()` 只返回系统默认，显式绑定到它反而可能覆盖 Windows 的按应用端点策略。像 PotPlayer 这类原生播放器都是不锁设备、交给系统路由。于是 1.2.11 把显式绑定去掉，改成：不固定设备，交给 Windows 选默认或按应用端点，系统默认变化时重建输出。

验证是在离屏模式下做的：合成一段 FLAC 播放，分别测「播放中重绑」和「暂停中重绑」，断言设备、音量、播放/暂停状态、进度都保持。真实耳机热插拔没法在当前机器上模拟，我标了未验证，留给多端点机器复测。

一个没修完的尾巴：Windows 改「按应用输出」的瞬间不会立刻切过去——Qt 没有公开 API 查「当前应用应该用哪个端点」，`audioOutputsChanged` 也不总在按应用设置变化时触发。结果是「最终正确、不秒切」，要等下一次重建（切歌、停止再播、重启）才重新路由。我没为了秒切去反复重建音频流，那会带来爆音和进度跳变。

## 通道顺序和脚本排序，是两件事

自定义源是下载通道之一，走洛雪的 `globalThis.lx` 协议：脚本只负责把歌曲 ID 换成播放地址。三条通道按设置里的顺序依次尝试：`musicdl` 搜索、自定义源、官方接口。

这里我栽过一次。1.2.7 到 1.2.8 那阵，我把下载顺序改成了「自定义源全部失败再走 musicdl/官方」，等于强制洛雪优先；还顺手在音源列表里插了一个「星海」专用条目。用户直接点破了两点：通道顺序必须按设置里定义的来，自定义源排第几就第几；插专用条目违反干净原则。

根因是我把两件事混成了一件：**下载通道的先后**，和**自定义源内部脚本的先后**。前者是「musicdl / 自定义源 / 官方接口」三选排序，由设置决定；后者是同一通道里装了好几个源脚本时，谁先试。

1.2.9 把两者拆开：

- 通道严格按设置顺序执行，自定义源不强制排在 musicdl 或官方前面。
- 手动「上移 / 下移」和「按测试结果排序」只动 `source_script` 表里的 `priority` 字段，按成功优先、延迟升序、失败最后重排，写回数据库。
- 「按测试结果排序」永远不碰通道顺序。健康检查只拿云端「我喜欢的音乐」里第一首未下载的歌当样本，测完按勾选决定要不要自动重排。

下载时某个源解析或下载失败会自动换同通道的下一个源，全部自定义源都失败才继续下一个下载通道。通道顺序本身不再被任何自动逻辑改动。

自动获取最新音源也是这条路：从 `data/source_repos.json` 里配置的公开仓库发现脚本，校验是否含 `@name`、`sources`、`lx` 初始化这些特征，写进临时目录，再用云端歌单里第一首未下载的歌逐个 `resolve`，只有真的解析出地址的脚本才复制成 `auto-*.js`。这里还踩过一个识别坑：1.2.7 之前校验只认 `lx.send`，把用 `send(EVENT_NAMES.inited, ...)` 写法的星海误判成无效源；改成兼容 `send(` 和 `EVENT_NAMES.inited` 几种写法后才通过。

## 先认身份，再比元数据

通道拿回来的候选，怎么确定是「同一首歌」？分两种。

官方接口和自定义源拿到的本来就是同一个网易 `song_id`，属于同一首歌，不需要猜；同一 `song_id` 只有一个候选时直接采用。`musicdl` 是搜索来的，要过四道规则：歌名、歌手、专辑归一化后完全相等，时长按整秒相等。

归一化只动四处：全角转半角、合并空白、大小写、繁简中文，外加清掉零宽字符。不剥 `feat.`、`Live`、`Remix`，也不做模糊包含——那会改变含义。四道全过还不够，还必须唯一：两个候选都合规，同样转人工。

转人工不是失败。待确认列表列出每个候选的来源、标题、歌手、专辑、时长、音质、大小，以及没过哪条规则；可以试听，也可以指定一条入库。自动流程只接受无损，320K 必须人工点头。

这条匹配规则和「时长整秒比对」是同一条防线：名字对得上但其实是伴奏、翻唱、同名不同版本的，四道规则和唯一性挡掉大部分；剩下挡不住的靠下载后的实际时长比对兜底——那是发现「下错歌」最快的方法。

## 假无损：灰区不是放行，公式也不能写反

归档要回答「文件是不是真的无损」。320K 转码改个后缀就是 FLAC，播放器看不出来，所以不能信扩展名，得解码一段真实 PCM 做 FFT。

这一块我犯的错不止一处。最早写方案文档时，高频落差的公式符号写反了：文档写 18–20k − 20–22k，代码算的是 `mean(20–22k) − mean(18–20k)`。更早的版本还有个一刀切：采样率不高于 44.1 kHz 就直接返回「未知」放行，导致普通 CD 音质的 FLAC 全都不做频谱判定。以及，人工接受 320K 时仍被假无损闸门拒绝——`expected_lossless=False` 这条人工路径，早期版本仍无条件跑了判定函数，非无损容器必然被判假。

逐行核对 `audio.py` 和 `download.py` 才看清：早期代码只在 `verdict == "fake"` 时才拦，`suspicious` 和 `unknown` 其实都放行了，和 README 里「灰区转人工」对不上。

现在的判定统一在 `classify_metrics` 里，三档：

| 信号 | 结果 |
| --- | --- |
| 平均码率低于 400 kbps | 判假，丢弃 |
| 平均码率 400–600 kbps | 灰区，转人工 |
| 频谱截止低于 18 kHz | 判假，丢弃 |
| 频谱截止 18–20 kHz | 灰区，转人工 |
| 顶部八度出现 ≥ 40 dB 断崖 | 灰区，转人工 |
| 其余 | 通过 |

采样率不再一刀切，44.1 kHz 也做频谱；人工路径跳过自动假无损闸门，但仍校验时长、清洗和标签。验证用的是合成音频：`make_flac(cutoff=16000/20000/22000)` 分别得到 fake / suspicious / ok，低码率得 fake，`test_spectrum.py` 覆盖了这几档。

频谱取样有讲究：取中段 60 秒、从全曲 33% 处开始，避开 intro 和 fade——这两段不代表编码器的带宽。灰区和无法判定都进「待确认」，不自动入库、也不直接扔，由人听过再决定；解码失败同样转人工，不当通过。

顺带一个小坑：静态频谱在很宽的控件上会崩，报 `频谱生成失败: index 128 out-of-bounds in add.reduceat`。根因是控件宽度大于分析的帧数时，时间轴分桶的最后一个起始索引等于帧数，`reduceat` 越界。修法是频率和时间分桶索引都 clip 到 `len-1`，重复索引用计数下限 1 兜底。

播放器复用同一份解码 PCM：下载闸门看的频谱和播放页看到的整首频谱图，走同一个分析函数，所以「图上看着是转码」和「判定拦掉」不会打架。静态频谱点开才生成，用 Spek 默认的 SoX 色阶（0 到 -120 dB），在内存里算，不缓存、不落盘；实时频谱只在「频谱」页启动，读当前位置附近一小段 PCM，以水平中轴上下镜像、柱子紧贴，离开页面就停。

## 三条轴，七个列表，一次原子入库

状态是这类工具最容易写坏的地方：用一个 `state` 字段同时表示「在不在歌单」和「下没下载」。NeteaseVault 拆成互不覆盖的几条轴：

- `cloud_present` / `cloud_playable`：云端现在有没有、能不能播，只由同步写。
- `local_state`：`none` / `downloaded` / `pending_review` / `match_failed`，只由下载流程写。
- `local_only`：磁盘上有文件、云端没有对应记录。

同步只更新云端字段，绝不碰 `local_state`。取消喜欢再加回来，下载状态照样在。同步按云端顺序读全部曲目，记录顺序、收藏时间、时长、云端音质上限和可播状态；第一次慢，之后只更新变化，网络请求只在点「同步」时发生。

![三条轴推导出七个列表](images/views.webp)

七个列表不单独存「这首歌属于哪个列表」，全部由 SQL 谓词推导，定义在 `states.py` 的 `LIST_SQL` 里。顶部统计只算云端歌单，一首歌离开歌单后「已下载」的数字跟着降，不会一直虚高。

三轴不是一开始就有。最早版本的 `track` 表只有一个 `state` 字段，同时表示「在不在歌单」和「下没下载」。迁到三轴时做了一次回填：旧 `state` 映射到 `local_state`（`in_library`→`downloaded`、`pending_review`→`pending_review`、`match_failed`→`match_failed`、其余→`none`），`removed_cloud` 映射成 `cloud_present=0` 并补 `removed_at`。回填完删掉旧列；旧版 SQLite 不支持 `DROP COLUMN`，就改名旧表、按新 schema 重建、再插回数据。这段逻辑现在还在 `_migrate()` 里，新装和升级走同一段代码。

![一次下载的流水线](images/flow.webp)

入库是原子操作：先下载到 `data/staging/<song_id>/`，`.part` 分块写入，支持暂停、继续、取消，失败按设置重试、并发和搜索/下载限速可调；容器嗅探、实际时长整秒比对、PCM 频谱、清洗复检全过了，才 `shutil.move` 进 `music/`。文件名固定 `歌名 - 歌手.ext`，非法字符替换、重名加序号。任何一步失败都 `rmtree` 掉整个暂存目录，`music/` 里不留半成品。清洗只留四项标签（`TITLE` / `ARTIST` / `ALBUM` / `LYRICS`），FLAC 只留 STREAMINFO 和标签块，剥完再解析一遍复核。

凭证用 Windows DPAPI 加密。扫码登录已被网易关闭（服务端返回 8821），现在只有 Cookie：登录 music.163.com，`F12` → `Application` → `Cookies`，复制 `MUSIC_U`。程序能解析整段请求头、分号列表和 JSON 三种粘贴形态，保存前验证并显示昵称和 UID；加密调 `CryptProtectData`，带 `CRYPTPROTECT_UI_FORBIDDEN`，绑定当前 Windows 用户的登录凭据，换账户读不出明文。

## 1.2.12：参数化与路径边界

最后一批改动是安全加固。数据库查询全部改成 `?` 占位；列表谓词用白名单常量加 `LIMIT` 绑定。连接参数也顺带补全：WAL 日志、`busy_timeout=5000`、外键开启，多线程读写同一库时不至于锁死。唯一没法参数化的是「列名来自 `PRAGMA table_info`」的重建表场景，列名不是值、不能绑参，就用 `_quote_ident` 把引号转义：

```python
def _quote_ident(name: str) -> str:
    return '"' + name.replace('"', '""') + '"'
```

自定义源下载和引擎脚本加了路径边界校验，子进程调用改成无 shell 模式：Node 引擎用 argv 列表 `shell=False` 启动，下载 URL 先过一道白名单，只允许 http/https 且有 hostname，才交给系统 curl。代码里留下的 `nosemgrep` 注释标记的是扫描器曾报过的动态 SQL 和子进程调用点——改成参数化和无 shell 之后，这些注释说明「这里是剩下的、已确认安全的动态拼装」。

## 安装与构建

从源码构建跑 `build.ps1`：先生成 onedir 程序，跑一次 `--selftest`，再编译绿色安装器。装好后目录只有三样：`NeteaseVault.exe`、`data/`、`music/`，没有 `_internal`，不写注册表、不写 `%AppData%`；整个目录可以搬走，删除目录就是卸载。运行期除 `music/` 外的写入都在 `data/`，数据库、凭证、配置、日志、缓存、暂存和自定义源脚本都在里面。

## 边界

- 只支持 Windows 10/11，只归档「我喜欢的音乐」一个歌单，不做云端上传、不能编辑歌单。
- 不内置任何音源密钥或账号；自定义源来自公开第三方仓库，失效是常态。
- 假无损是启发式，不保证识别所有转码，灰区和无法判定都交给人。
- 按应用指定输出不会秒切，最终正确但不即时；真实耳机热插拔未在多端点机器复测。
- 网易的接口和风控随时可能变，同步或下载失效属于正常损耗。
