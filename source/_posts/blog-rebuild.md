改一篇旧文，最费事的一步往往是找图。封面在 `source/img/projects/`，流程图也在那里，文件名靠 `neteasevault-flow.webp` 这种前缀区分项目。文章一多，这个目录就乱成一锅：哪张图属于哪篇、删文章时哪张能一起删，全靠记忆。

这次把结构改了：一篇文章一个文件夹，图片跟着文章走，正文只写 `images/...` 的相对路径。顺手做了一个本地写作台，把选文章、写正文、贴图、改元信息、预览、提交和推送收进一个界面。

## `post_asset_folder` 与两种目录布局

最初的想法是在 `source/img/projects/` 下面按项目建子目录，文章里写 `/img/projects/neteasevault/cover.webp`。改动最小，但图片和文章仍然是两棵树，删文章、改 slug、迁移文章时都要手动对一遍。

Hexo 有「文章资源文件夹」机制：`post_asset_folder: true` 时，`source/_posts/foo.md` 可以配一个同级的 `source/_posts/foo/` 目录，构建时把里面的文件复制到文章 URL 下面。再打开 `hexo-renderer-marked` 的 `postAsset`，正文里的 `![](bar.webp)` 会解析成这篇文章的资源，输出 `/2026/11/28/foo/bar.webp`。

实际测了两种目录：

```text
source/_posts/foo.md
source/_posts/foo/images/cover.webp
正文：![](images/cover.webp)

source/_posts/foo/index.md
source/_posts/foo/images/cover.webp
正文：![](images/cover.webp)
```

第一种正常。第二种不行：Hexo 计算资源目录时用的是「文章源文件去掉扩展名」：`foo/index.md` 去掉扩展名是 `foo/index`，对应资源目录是 `foo/index/`，图片放在 `foo/images/` 就成了另一个目录里的文件，不会被当作这篇文章的资源。要让它工作得改 Hexo 的资源处理，或者接受一个 `index` 子目录，得不偿失。

所以用第一种：文章文件在 `_posts/` 根下，图片在同名文件夹的 `images/` 里。文章 URL 完全不变，旧链接继续有效；删文章时整个文件夹一起处理，不再留孤儿图片。

## 迁移与验证

现有四篇文章一共九张图。迁移就是 `git mv` 到各自的 `images/`，再把正文里的 `/img/projects/...` 换成 `images/...`。需要验证的是三件事：

1. 构建后每张图都在文章 URL 下，不在 `/img/`。
2. 文章页面里的 `<img src>` 指向新路径，且文件存在。
3. 旧文章 URL 没变。

`npx hexo clean && npx hexo generate` 之后，构建输出里能看到：

```text
Generated: 2026/11/11/neteasevault/images/cover.webp
Generated: 2026/10/18/dsh-loop-guard/images/flow.webp
...
```

页面里的引用也变成了 `/2026/11/11/neteasevault/images/cover.webp`。写了一个小脚本，把每篇文章的 Markdown 图片引用抽出来，按「文章 slug + 文件名」去磁盘上查，九张全部命中；再检查 `source/img/projects/` 是否还有残留引用，零命中。这套检查跑在提交之前，任何一个路径对不上都会先停下来改，而不是直接带上线。

## 写作台独立于博客仓库

写作台没有放进博客仓库。公开仓库只放站点运行需要的东西，一个本地编辑器、它的依赖和构建产物不属于这个范围；编辑器有自己的依赖和发布节奏，和 Hexo 的构建链绑在一起会互相拖累。

它现在是一个独立目录，启动后跑一个只监听 `127.0.0.1` 的 Node 服务，浏览器打开就是界面。前端是 Vue 3 + CodeMirror 6，后端是 Express，和博客仓库通过配置里的路径关联。技术选型没有特别的理由：CodeMirror 的 Markdown 编辑和选区操作够用，Vue 的状态管理写这种表单界面比手写 DOM 省事，Node 端直接复用 Hexo 仓库已有的环境。

界面分三块：左边文章列表，中间编辑器和预览，右边信息、图片、检查、Git 四个面板。顶部只留保存、预览、主题和更多操作，避免把写作界面做成 IDE。

## 图片从剪贴板到文章目录

写作台里贴图有两步：先把文件变成 WebP，再决定它放在哪。

服务端用 `sharp` 处理上传：读入原始字节，按 EXIF 旋转，宽度超过 1600 就等比缩小，然后按质量 85 输出 WebP。原图不留在博客仓库，默认存在写作台自己的 `.data/originals/` 里，方便以后重新裁；关掉「保留原图」就只留 WebP。文件名会转成小写 ASCII，中文名会变成 `image`，重名自动加 `-2`。

图片写入 `source/_posts/<slug>/images/`，接口返回文件名；前端在光标处插入：

```markdown
![图片说明](images/cover.webp)
```

路径写 `images/...`，不写 `/img/...`，也不写 `./`。`images/` 是相对文章资源根的路径，Hexo 的 `postAsset` 能解析，写作台自己的预览也能解析。

预览的图片路径是另一套映射。Markdown 渲染器拿到的 `images/cover.webp` 是相对路径，浏览器会按当前页面 URL 去请求，直接渲染会 404。写作台在 markdown-it 的 image renderer 里把它改写成 `/media/<slug>/images/cover.webp`，后端从这个文章目录读文件。老文章里如果还有 `/img/...` 的引用，就走 `/media/global/...`，从 `source/img/` 读，保证迁移期间不炸。这套 `/media/` 映射只在写作台内部生效，落盘到 Markdown 里的仍是 `images/` 相对路径，两者不混。

## 日期多了八小时

写作台上线后第一个 bug 是日期。打开 `neteasevault.md`，front matter 里是 `2026-11-11 21:45:00`，界面显示成 `2026-11-12 05:45:00`，保存一次就写错。

原因是 `gray-matter` 底下的 `js-yaml` 把不带时区的 YAML 时间戳当成了 UTC：`2026-11-11 21:45:00` 被解析成 UTC 的那一刻，再用本地时区格式化，就多了八小时。Hexo 自己按站点时区处理，不受这个影响；写作台如果直接信 `js-yaml` 的 Date，就会把每篇文章的日期往后推一天。

修法是在解析时保留原文：先读出 front matter 里的 `date:` 和 `updated:` 原始字符串，覆盖掉 `js-yaml` 解析出来的 Date，再交给自己的日期函数。写回去的时候也统一成 `YYYY-MM-DD HH:mm:ss`，不写 ISO 带 Z 的形式。加了一条测试：同样的 front matter 解析再序列化，日期必须一字不差。

这个错误不会触发任何报错：构建正常，文章也能显示，只是日期错了。没注意到的话，四篇文章的发布时间会一起漂移。

## 自动保存的「看起来没改」

编辑器有自动保存，输入停止 1.4 秒后写盘。第一版实现里，保存成功后会把服务端返回的 `meta` 和 `content` 写回响应式状态，结果保存动作本身又触发了「内容变了」的 watcher，界面一直显示「未保存」，自动保存反复发请求。

根子是「用变化事件判断脏状态」：加载文章、保存回写、用户输入都会改变同一份状态，但只有第三种应该标记为脏。修法是在加载和保存回写时置一个 `hydrating` 标志，等 Vue 的 `nextTick` 把这次变更 flush 掉再清掉；只有标志为 false 时的变化才 `dirty = true`。另外用一个递增的 `changeSeq` 记录保存期间有没有新输入：保存请求发出时记下序号，响应回来如果序号变了，就不拿服务端结果覆盖用户刚敲的内容，保留脏状态再存一次。这样在保存请求还没返回时又敲了字，新输入也不会被旧响应冲掉。

缺少这层隔离时，保存回写会再次触发「内容变了」，自动保存进入循环。加上 `hydrating` 和序号判断之后，保存动作本身不再产生新的脏状态。

## Git 面板只提交选中的文件

写作台的 Git 面板先跑 `git status --porcelain=v1 -z` 列出改动，前端给每个文件一个复选框，默认全选，用户可以取消；提交时只 `git add -A -- <选中的路径>`，再用配置里的作者信息 commit。

作者信息单独放在写作台配置里，不依赖博客仓库的全局 Git 配置。博客的提交署名是仓库约定的 noreply 地址，写作台用 `GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL` 环境变量覆盖，避免把本机其他项目的署名带进来。推送就是普通的 `git push`，不做强推；遇到分支保护或凭据缺失，错误原样显示在面板里，不去猜。

提交信息默认给一句「更新文章：标题」，但可以改。写作台不会自动提交，也不会在保存时偷偷推送；保存、提交、推送是三个动作。

## 文风检查只提示，不改稿

右侧的「检查」面板会扫几类东西：套话和提醒式过渡、抽象流行词、列表占比过高、超长段落、连续感叹号。

它不自动改，也不给分数，只列出行号和原文片段；点一下跳到对应行，自己决定删不删。规则写在服务端，测试里覆盖了「代码块里的词不算」「行号要对得上」这些边界。这套检查的作用是在赶稿时提示「这段是不是又写成 PPT 了」，改不改由写的人决定。

## 三次构建的结果

改完结构后跑了三次构建：

- 迁移后、改文章前：96 个文件，九张图全部在文章目录下。
- 四篇重写后：文章页的每张图都返回 HTTP 200，没有 404。
- 写作台改完一篇测试文章再删除：`git status` 干净，回收目录里有文件，博客仓库没有残留。

写作台的测试是 `node --test`，覆盖 front matter 往返、日期、slug 校验、路径越界、文风规则；前端没有做单元测试，用浏览器实际点过新建、改标题、自动保存、删除、切主题、Lint、Git 状态和本地 Hexo 预览。本地 Hexo 预览直接启动 `hexo server`，用的是 Hexo 自己的渲染，没有另写一套。

## 没做到的几件事

- 写作台只在本机跑，监听 `127.0.0.1`，没有登录和多用户。
- 图片统一转 WebP，质量 85、宽 1600 是默认值；需要原图时去 `.data/originals/` 找，仓库里不存。
- 草稿用 `published: false` 表示，Hexo 不会生成；审核后再切发布，没有额外的审核系统。
- 它不替代 Hexo 的主题、部署和缓存逻辑，只负责文章文件、图片和 Git。
- 文章 URL 取决于文件名和日期；改 slug 会改 URL，写作台会提示，但不会自动做重定向。

结构改完后，改文章时不需要再确认图片位置。四篇文章、九张图现在各归各的 `images/` 文件夹，写的时候图就在这篇的文件夹里，预览和构建走同一条相对路径，提交时 Git 面板也只看到这篇文章的文件。对一个长期维护的博客来说，这比多一个功能齐全但流程割裂的编辑器更实用。
